# Architecture decisions

The web app is a presentation client. The Node server is the sole authority for room membership, player presence, game state, card randomness, actions, and virtual-chip settlement. Prisma persists durable identities and outcomes; Redis is reserved for ephemeral room and presence coordination.

Phase 2 room lifecycle is implemented by `apps/server/src/rooms.ts`. `RoomManager` owns code generation, membership, reconnects, readiness, host reassignment, and the gate that moves a ready room to `PLAYING`. Socket.IO only translates events into domain operations and broadcasts authoritative `RoomSummary` projections. `RoomStateStore` is the explicit storage boundary; `InMemoryRoomStateStore` is used by the current single-process server and tests, while a Redis implementation can be introduced without changing the domain or transport layer.

`packages/shared/src/auth.ts` defines the application session shape and provider boundary. Phase 6 provides a safe `MemoryAuthBoundary` adapter with scrypt password hashing, guest sessions, email registration/login, and Google capability negotiation; production provider credentials can be supplied through the same contract without coupling game code to a provider. The server requires a valid bearer session for social APIs and can authenticate Socket.IO connections through `handshake.auth.sessionToken`.

Phase 6 adds profile, friendship, wallet, notifications, invitation, history, and statistics projections in `apps/server/src/platform.ts`. The in-memory service is deterministic for local development and tests; `apps/server/src/prisma.ts` provides the Prisma client and transactional wallet persistence seam. Room chat checks authenticated room membership and caps message size before broadcasting. The web app exposes `/lobby`, `/auth`, `/profile`, `/friends`, `/history`, and `/settings` surfaces; game routes remain server-authoritative.

Each game implements a transport-independent `GameEngine` contract. Phase 3 adds `PokerEngine` in `packages/game-engine/src/poker.ts`. The engine owns a cryptographically shuffled deck, private hole cards, dealer/blind rotation, turn validation, betting rounds, hand evaluation, side-pot construction, and split-pot settlement. Its internal `PokerState` is retained only by the server; `toPublicState` omits hole cards, and private projections are addressed to exactly one player.

Phase 4 adds `RummyEngine` in `packages/game-engine/src/rummy.ts`. It uses two shuffled 52-card decks plus printed jokers, deals 13 cards, selects a wild joker, and enforces server-authoritative draw/discard turns. Declaration validation is pure-function based: every card must be partitioned into groups with at least one pure sequence and two sequences total; sets and impure sequences may use wild jokers. Invalid declarations receive the capped 80-point penalty, while opponents receive deadwood scores. Public projections expose counts, scores, piles, and turn order only; each player's hand is emitted through that player's private Socket.IO event.

Phase 5 adds `PotEngine` in `packages/game-engine/src/pot.ts` for In-Between/Acey-Deucey. It creates a cryptographically shuffled single deck, supports configurable ace-low or ace-high ranking, evaluates bets only when the third card is strictly between the two displayed cards, treats equal and consecutive cards as losses, and supports a no-wager pass. Bets are integer-validated against configurable minimum, maximum, and player balance limits; wins settle at 1:1, while losses and passes settle without credit. Request IDs are retained to reject duplicate actions, and turns rotate only to players with enough balance for the minimum bet.

Socket.IO starts a Poker, Rummy, or Pot hand with `game:start` and forwards player actions through `game:action`. The server overwrites the command actor with the authenticated room seat, applies the command to the authoritative engine state, broadcasts the public projection, and emits each private projection only to its matching socket. The client tables are presentation surfaces for those contracts; they do not calculate outcomes or mutate authoritative state.

## Phase 7 production boundary

The HTTP boundary disables framework identification, emits baseline security headers, limits JSON and Socket.IO payload sizes, validates exact configured origins, and applies bounded in-memory rate limits to API, authentication, and chat traffic. `/health/live` is a process liveness probe; `/health/ready` checks PostgreSQL reachability and reports Redis configuration without claiming distributed Redis-backed room state.

Vercel builds `apps/web` from `vercel.json`. Railway builds `apps/server/Dockerfile`, runs behind its health check, and receives PostgreSQL, managed Redis, CORS, and authentication configuration through its secret store. CI runs Prisma generation, typechecking, tests, builds, and `git diff --check`. External provider provisioning and deployment credentials remain operator-owned.
